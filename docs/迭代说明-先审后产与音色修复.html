先审后产 + 音色修复

一次交互流程升级与一次配音缺陷修复的记录 —— 生成改为两段式；音色切换变得真实可感。

日期：2026-09-22 配套：创作台 V2 状态：全部验证通过
01 · 结论先行两件事的结果

流程改动：有意义，已实施；音色缺陷：根因已定位并修复

结论

「先出文本、审核后再出片」的两段式流程值得做 —— 它把人的审核放在成本最低、返工代价最小的环节，同时让音色与配乐在重成本环节开始前一次定死。本页同时记录配音音色切换失效问题的根因与修复。

02 · 评估为什么值得做

四条理由，与三条要接受的代价

把「选诗 → 直接等出片」改为「选诗 → 审文案、定配置 → 确认出片」，收益与代价都很明确：

  • 成本结构 —— 文本是最便宜的一环，画面（尤其将来接图生视频）与配音是最贵的环节。审核放在最便宜的环节，避免重成本产出整段报废。
  • 质量门槛 —— 释义与文案是全片的「魂」。错字一旦烧进字幕和配音，返工代价高；先审后产让问题止步于一步文本。
  • 一致性与体验 —— 音色、配乐提前定死，后续不再返工（本次音色问题的摩擦正出在「中途换设置」）；确认按钮给用户一个明确的控制点。
  • 与产品逻辑同向 —— 「先脚本、后制作」是内容生产工具的通用水位线，也呼应路书「按分镜批量生成、人工挑片」的成本主张。

需要接受的代价：① 多一次点击（以一次确认换成本与质量）；② 工作台状态机变复杂（analyzing / review / rendering / done 四态，由实现承担）；③ 两段之间失败需要断点续跑——由内容哈希缓存兜底（已在机制内）。

03 · 实现现在的工作流

四步走：解析 → 审核 → 确认 → 迭代

第一步

生成解析与文案 —— 只跑「文本 + 分镜」两道工序，不消耗生图与配音。离线通道瞬时完成；接大模型时只花一次文本调用。

任务 API：POST /api/jobs · mode=analyze

第二步

审核修改，定音色配乐 —— 逐句释义 / 背景 / 文案可逐条编辑；右栏「待确认」块实时显示将使用的画面通道、音色与配乐（含本机音色映射说明）。

数据流：analysis.json（可编辑）· 音色档案 = 音色 + 语速 + 音高塑形

第三步

确认，生成成片 —— 点「开始生成成片」后依次执行：分镜意境图 → 朗诵配音 → 字幕烧制与合成；五段进度实时回传。

任务 API：POST /api/jobs · mode=render（带已审核解析）

第四步

迭代 —— 成片后继续修改文案或换音色，点「重新合成」会复用已出画面，只重做声音与合成，1-3 分钟出新片。

复用判定：同一首诗 + 已有成片 → 图片复用缓存

兼容性说明

一次性全链路（mode=full）保留为兜底路径；历史作品、命令行 run 与批量 batch 不受影响。审阅期的分析任务不进入作品库（无成片清单）。

04 · 音色修复根因与方案

「换了音色听不出来」—— 因为机器上只有一个音色

根因：本机只安装了一个中文语音（Microsoft Huihui）。旧实现里，三个档案（云阙 / 清徵 / 松风）实际都落在同一个音色上，彼此只有语速差（-1 / -2 / -3）——切换发生了，但听感几乎一样，于是看起来「未生效」。

修复分三层：① 音高塑形 —— 云阙 ×0.85 低音、松风 ×0.78 深低音（降调不变速的音频管线），三档从「同一把嗓子」变成可辨的三档；② 映射透明化 —— 工作台直接显示「本机映射」：哪个档案落在哪个实际音色、是否经过塑形；③ 回退保护 —— 在装有 Kangkang / Yunyang 的系统上直接使用理想音色、不做塑形；分段合成失败自动重试一次。

验证项结果说明
三档互异✔ 两两不同同一句话：4085 / 4551 / 5070 ms，文件内容两两不同
音高确实降低✔ 单调下降频谱质心：清徵 1547 Hz → 云阙 1413 Hz → 松风 1273 Hz
降调不变速✔ ±0.3%修复前后同一档案时长 9236 → 9216 ms（语速与画面时长不受影响）
成片级验证✔ 重渲完成云阙版《春晓》81 秒成片；音频段与修复前内容不同
试听样例

三档各选同句录音，位于 docs/assets/voice-samples/：清徵 · 云阙 · 松风。单音色塑形是「尽力而为」的近似方案；接入云端音色（openai 兼容通道）后可换成真正不同的男声 / 女声。
